# MTGNissa 功能需求

## 文档状态

- 状态：需求草案
- 范围：卡牌查看、个人卡牌、愿望单、卡组和操作日志
- 暂不包含：数据库表、API、完整查询条件和页面具体布局

## 1. 功能范围

系统包含：

```text
卡牌中心
├── 全部卡牌
├── 我的卡牌
├── 愿望单
└── 卡牌详情

卡组
├── 卡组列表
├── 卡组编辑
├── 卡组展示
└── 卡组统计

操作日志
├── 每日操作汇总
└── 操作明细
```

### 1.1 页面身份标识

部署实例可以通过配置文件提供 `app.display_name`，用于表示当前是谁的卡牌库。该配置可省略，默认值为空字符串。

页面标题或全局导航区域按统一逻辑展示该配置值。应用不裁剪、不校验或分支处理该字符串；值为空时展示结果自然为空字符串。

`display_name` 只用于展示，不代表登录账号、认证主体或数据权限，也不写入个人数据库或用户操作日志。修改配置并重启服务后，页面使用新名称。

全部卡牌、我的卡牌和愿望单应复用卡牌列表、详情及管理操作，不建立三套重复页面。

## 2. 卡牌查看与检索

已确认需要：

- 查看 Set 列表
- 选择 Set 查看该 Set 的卡牌
- 根据卡名搜索
- 根据费用搜索
- 从检索结果进入卡牌详情
- 从列表修改拥有数量
- 从列表管理愿望单

完整查询能力暂不确定，后续根据参考网站交互、卡牌数据库模型、数据库实际字段以及索引和查询能力设计。

不要求实现完整 Scryfall 搜索语法。

## 3. 卡牌详情

卡牌详情以具体印刷版本为入口：

```text
Set + 收藏编号
```

展示内容包括：

- 卡图
- 双面牌或多牌面的所有内容
- 卡名
- 费用
- 类型
- 卡牌文字
- 力量、防御、忠诚等属性
- Set
- 收藏编号
- 稀有度
- 印刷版本语言
- 数据库提供的其他必要字段

### 3.1 说明语言

卡牌详情不提供说明语言切换。

卡牌名称、类型、规则文字等说明内容：

```text
优先使用配置文件指定语言
    ↓
不存在时显示英文
```

说明语言与实体卡语言相互独立。

例如拥有日文实体卡、系统配置为简体中文时：

```text
版本语言：日文
说明文字：简体中文
```

简体中文说明不存在时显示英文。

### 3.2 印刷版本

详情页展示同一逻辑卡牌的全部印刷版本：

- 不同 Set
- 不同收藏编号
- 不同语言
- 各版本拥有数量
- 各版本愿望单状态

支持切换到其他印刷版本详情。

### 3.3 拥有数量

普通卡和闪卡在同一个数量字段中展示：

```text
普通卡数量:闪卡数量*
```

例如：

```text
3:1*
```

表示普通卡 3 张、闪卡 1 张。

详情页支持分别增加或减少普通卡和闪卡数量。

## 4. 我的卡牌

只展示拥有数量大于零的卡牌。

收藏数量至少区分：

```text
逻辑卡牌
+ Set
+ 收藏编号
+ 语言
+ 普通/闪卡
```

不为每一张实体卡建立独立档案。

### 4.1 排序

支持：

- 按 Set 和收藏编号排序
- 按颜色费用排序
- 按名称排序

颜色费用和收藏编号的具体排序规则，根据卡牌数据库模型确定。

### 4.2 Set 合并

按 Set 排序时不提供跨 Set 合并。

按颜色费用或名称排序时提供：

```text
[ ] 合并不同 Set
```

关闭时，不同印刷版本展示为多张卡：

```text
Lightning Bolt / M11 / 2:1*
Lightning Bolt / M10 / 3:0*
Lightning Bolt / 2X2 / 1:1*
```

这些卡牌按照排序结果连续展示。

开启时，同一逻辑卡牌展示为一张汇总卡：

```text
Lightning Bolt / 全部 Set / 6:2*
```

汇总卡可以查看各 Set 明细。

### 4.3 语言合并

收藏严格区分语言，并提供：

```text
[ ] 合并不同语言
```

关闭时：

```text
Lightning Bolt / M11 / 英文 / 2:1*
Lightning Bolt / M11 / 日文 / 1:0*
Lightning Bolt / M11 / 简中 / 3:0*
```

开启时：

```text
Lightning Bolt / M11 / 全部语言 / 6:1*
```

汇总卡可以查看语言明细。

### 4.4 合并组合

| Set 合并 | 语言合并 | 展示单位 |
| --- | --- | --- |
| 关闭 | 关闭 | 每个 Set、每种语言分别展示 |
| 开启 | 关闭 | 相同语言合并不同 Set |
| 关闭 | 开启 | 相同 Set 合并不同语言 |
| 开启 | 开启 | 每个逻辑卡牌展示一张 |

普通和闪卡始终通过 `普通:闪*` 汇总。

## 5. 愿望单

愿望单只展示用户明确标记的印刷版本。

愿望项严格区分：

```text
Set
+ 收藏编号
+ 语言
```

不跨 Set 合并，不跨语言合并。

愿望单不记录：

- 目标数量
- 闪卡偏好
- 备注
- 优先级

愿望项只支持：

- 加入愿望单
- 移出愿望单

不提供修改语言操作。需要改变语言时：

```text
移出原愿望项
    ↓
使用新语言重新加入
```

即使已经拥有该版本，也不自动移出愿望单。

可以从以下位置管理愿望单：

- 全部卡牌
- 我的卡牌
- 卡牌详情
- 愿望单

## 6. 卡牌中心复合

全部卡牌、我的卡牌和愿望单共享：

- 搜索与筛选
- 排序
- 卡牌列表或图片展示
- 卡牌详情入口
- 普通卡数量操作
- 闪卡数量操作
- 愿望单操作

页面可以通过范围切换实现：

```text
[全部卡牌] [我的卡牌] [愿望单]
```

具体使用标签页、独立路由或组合页面，在前端设计阶段确定。

## 7. 卡组列表

支持：

- 创建卡组
- 查看卡组
- 编辑卡组
- 修改卡组名称
- 复制卡组
- 删除卡组
- 查看更新时间
- 查看卡牌总数
- 查看异常卡牌数量
- 查看卡组统计

不进行卡组合法性校验。

## 8. 卡组编辑

使用简单文本编辑器编辑卡组。

基础格式：

```text
4 Lightning Bolt
2 Counterspell
1 Sol Ring
```

卡组记录：

```text
逻辑卡牌 + 编辑数量
```

不要求用户指定：

- Set
- 收藏编号
- 语言
- 普通或闪卡
- 展示版本

无法识别的行必须明确提示，不能静默丢弃。

卡组必须记录每张牌所属的分区，并按分区展示。至少支持：

- 主牌（mainboard）
- 备牌（sideboard）
- 指挥官（commander）
- 备选区（maybeboard）

同一逻辑卡牌可以分别出现在多个分区；每个分区内只保留一条数量汇总。分区在卡组中的展示顺序必须稳定。

分区为系统固定类型，不支持用户创建、重命名、删除或调整分区顺序。固定展示顺序为：指挥官、主牌、备牌、备选区；不存在的分区不显示。

主牌、备牌和指挥官计入卡组数量、拥有量比较和卡组统计；备选区只用于展示候选牌，不计入这些结果。

简单文本格式需要提供明确的分区标题语法。首个分区标题之前的卡牌行视为主牌；无法识别的分区标题与无法识别的卡牌行一样，必须明确提示，不能静默归入主牌。

## 9. 卡组展示版本

卡组不支持手动指定印刷版本。

系统自动选择展示版本：

```text
拥有的版本
    ↓
愿望单版本
    ↓
最新印刷版本
```

自动选择只决定卡组展示的卡图和印刷版本，不影响卡组记录。

选择版本时不考虑：

- 是否被其他卡组使用
- 所有卡组使用总数
- 当前卡组编辑数量
- 拥有数量是否足够
- 可用数量或分配数量

存在多个拥有版本或愿望版本时的同级选择规则，等待卡牌数据模型确认。

## 10. 卡组拥有数量

卡组中的实际拥有数量按逻辑卡牌汇总：

```text
所有 Set
+ 所有语言
+ 普通卡
+ 闪卡
```

每张卡计算：

- 当前卡组编辑数量
- 实际拥有数量
- 所有卡组编辑总数
- 使用该牌的卡组数量

## 11. 卡组异常状态

正常情况不显示状态。

异常状态互斥，只显示优先级最高的一项：

```text
数量不足
    ↓
被多个卡组占用
    ↓
正常无标识
```

### 11.1 数量不足

条件：

```text
当前卡组编辑数量 > 实际拥有数量
```

显示：

```text
数量不足 N
```

计算：

```text
N = 当前卡组编辑数量 - 实际拥有数量
```

### 11.2 被多个卡组占用

仅在当前卡组不存在“数量不足”时判断。

条件：

```text
使用该牌的卡组数量 > 1
且
所有卡组编辑总数 > 实际拥有数量
```

显示：

```text
被多个卡组占用 N
```

计算：

```text
N = 所有卡组编辑总数 - 实际拥有数量
```

### 11.3 判断顺序

```text
if 当前卡组数量 > 实际拥有数量
    显示「数量不足」
else if 使用卡组数 > 1
     且所有卡组数量 > 实际拥有数量
    显示「被多个卡组占用」
else
    不显示状态
```

### 11.4 示例

实际拥有 4 张：

| 当前卡组 | 所有卡组合计 | 使用卡组数 | 显示 |
| ---: | ---: | ---: | --- |
| 5 | 8 | 2 | `数量不足 1` |
| 4 | 8 | 2 | `被多个卡组占用 4` |
| 3 | 6 | 2 | `被多个卡组占用 2` |
| 2 | 4 | 2 | 不显示 |
| 4 | 4 | 1 | 不显示 |

异常状态不影响卡组保存和自动版本选择，不执行实体卡分配，只用于提示和统计。

## 12. 多卡组使用情况

卡牌详情或我的卡牌中展示逻辑卡牌的卡组使用情况：

```text
实际拥有：4
出现在 2 个卡组中
所有卡组编辑总数：8
跨卡组缺口：4
```

可以查看具体卡组：

```text
Burn：4
Modern Red：4
```

这属于统计，不代表具体实体卡已经分配给某个卡组。

## 13. 卡组统计

至少包括：

- 卡牌总数
- 不同逻辑卡牌数量
- 类型分布
- 颜色分布
- Mana Value 分布
- Mana Curve
- 土地与非地牌数量
- 数量不足的卡牌数量
- 被多个卡组占用的卡牌数量
- 总缺少数量
- 收藏满足率

具体统计字段以卡牌数据库提供的数据为准。

## 14. 操作日志

日志只记录以下 8 种操作：

```text
增加卡牌
减少卡牌
加入愿望单
移出愿望单
创建卡组
删除卡组
复制卡组
修改卡组
```

不记录普通查看和查询。

### 14.1 每日汇总

日志按日期分组。每天每种操作类型最多展示一条汇总记录：

```text
2026-09-24

增加卡牌    12
减少卡牌     3
加入愿望单   5
移出愿望单   1
创建卡组     1
删除卡组     1
复制卡组     2
修改卡组     4
```

当天没有发生的操作不显示。

### 14.2 卡牌操作明细

点击卡牌操作汇总，显示：

- 卡牌名
- 必要的 Set、收藏编号和语言
- 普通或闪卡
- 数量变化

示例：

```text
增加卡牌

Lightning Bolt · M11 · 英文 · 普通 +3
Lightning Bolt · M11 · 日文 · 闪卡 +1
Counterspell · 2X2 · 英文 · 普通 +2
```

愿望单明细：

```text
加入愿望单

Lightning Bolt · M11 · 日文
Counterspell · 2X2 · 英文
```

### 14.3 卡组操作明细

点击卡组操作汇总，只展示卡组名：

```text
修改卡组

Burn
Modern Red
Commander Atraxa
```

卡组重命名归入 `修改卡组`，只显示新名字，不显示旧名字。

同一次卡组修改无论调整多少张牌，都作为一次 `修改卡组` 操作，不展开卡组内部卡牌变化。

## 15. 加载卡牌数据

### 15.1 功能目标

服务需要提供卡牌数据加载功能，将指定目录中的卡牌 JSON 数据全量导入外置卡牌数据库。

- 这是系统维护功能，不是个人收藏、愿望单或卡组的导入功能。
- 只加载只读卡牌元数据库，不得修改个人数据数据库。
- 每次执行均为全量替换，不做增量更新、合并或单条修复。
- 加载后的卡牌表内容必须完全来自本次读取的 JSON 文件。
- `scryfall_card` 是卡牌、印刷版本及英文原文的实体数据源；卡牌查询、列表和详情必须以其记录为主体。
- `zhs_*.json` 是可选的简体中文翻译、本地化及辅助词典数据，只能覆盖或补充 Scryfall 实体的展示字段，不得独立产生卡牌实体。
- 中文字段缺失、为 `null` 或仅含空白时，必须回退使用 `scryfall_card` 的对应字段。

### 15.2 数据目录

卡牌 JSON 目录由 Docker 映射到容器外部，并通过配置指定容器内路径，例如：

```text
CARD_DATA_DIR=/data/card-data
```

要求：

- Docker volume 使用只读挂载。
- 接口不能接收客户端传入的任意目录或文件路径。
- 服务只能读取 `CARD_DATA_DIR` 下约定的文件。

### 15.3 必需文件

每次加载必须同时读取以下九个 NDJSON/JSONL 文件：

1. `scryfall_card.json`
2. `zhs_card.json`
3. `zhs_flavor.json`
4. `zhs_oracle.json`
5. `zhs_ruling.json`
6. `zhs_set.json`
7. `zhs_type.json`
8. `rulings.jsonl`
9. `oracle-tags.jsonl`

任意文件缺失、无法读取、为空或包含非法 JSON 时，加载失败，现有卡牌库必须保持不变。

### 15.4 操作前完整确认

在影响现有卡牌表之前，服务必须完整读取九个文件，而不是只检查文件存在或只读取第一行。

每个文件至少检查：

- 文件存在、是普通文件、可读且非空。
- 从第一行到文件末尾的每一行都能解析为 JSON 对象。
- 每行包含该对象的必需字段。
- 记录文件大小、总行数和 SHA-256。
- 已确认唯一的关联字段不存在重复值。
- `zhs_*.json` 通常只将各文件的关联键或组合唯一键视为非空必需字段；`zhs_ruling.comment` 还必须非空，因为它用于生成跨数据源稳定规则键。翻译字段仍允许为 `null`。

只有全部九个文件都完成预检后，才能进入数据库加载阶段。

### 15.5 加载方式

业务结果要求为：删除旧卡牌表，按固定 Schema 重新建表，并插入本次 JSON 的全部数据。

考虑到 MySQL DDL 会隐式提交，不能直接先删除正在使用的正式表，否则导入失败会留下空库或半成品库。实现时采用等价但更安全的方式：

1. 完成全部文件预检。
2. 创建一组新的临时卡牌表。
3. 再次流式读取九个文件并导入临时表。
4. 校验普通源表的导入行数与预检行数一致；合并后的 `zhs_ruling` 行数不得少于 `zhs_ruling.json` 的预检行数。
5. 再次确认文件大小和 SHA-256 未在导入期间变化。
6. 使用 MySQL 多表 `RENAME TABLE` 原子切换新旧表。
7. 切换成功后删除全部旧卡牌表。

在切换前发生任何错误时，只清理临时表，现有正式卡牌表保持不变。

### 15.6 表范围

加载逻辑只能操作以下固定白名单表：

- `scryfall_card`
- `zhs_card`
- `zhs_flavor`
- `zhs_oracle`
- `zhs_ruling`
- `scryfall_oracle_ruling`
- `oracle_tag`
- `oracle_tag_relation`
- `oracle_tagging`
- `zhs_set`
- `zhs_type`
- `scryfall_card_keyword`
- `scryfall_card_type`
- `scryfall_card_frame_effect`
- `scryfall_card_promo_type`
- `scryfall_set`
- `scryfall_color`
- `scryfall_language`
- `scryfall_layout`
- `scryfall_frame`
- `scryfall_frame_effect`
- `scryfall_finish`
- `scryfall_game`

禁止枚举数据库中的所有表后直接删除。执行前必须确认当前连接的数据库名称等于配置的卡牌数据库名称，防止误操作个人数据数据库。

### 15.7 导入要求

- NDJSON 必须逐行流式读取，不能将整个文件加载到内存。
- 标量 JSON 字段使用 MySQL 对应标量类型存入主表或字典表，不得将整行记录保存为单个 `document` JSON 列。
- 颜色、颜色标识、颜色指示符、工艺、游戏平台和 Attraction 灯号为取值受限的多值属性，在 `scryfall_card` 中使用可索引位掩码列保存。
- `produced_mana` 不使用字典或关联表；按源数组顺序以逗号连接后直接存入 `scryfall_card.produced_mana VARCHAR(64) NULL`，不限制元素值域。
- 关键词、类型词、牌框效果和推广类型通过多对多关联表保存。
- 源文件字符串主键去除首尾空白后，按 Unicode 不区分大小写比较重复；多值字符串派生关系采用相同的比较规则去重，并保留第一次出现的原始大小写，避免仅有大小写或首尾空白差异的数据与 MySQL `utf8mb4_unicode_ci` 唯一键规则冲突。
- 不建立费用符号关联表；完整费用保存在 `mana_cost`，法术力值查询使用 `cmc`，颜色查询使用颜色及颜色标识位掩码。
- `artist_ids` 按源数组顺序以逗号连接后保存到 `scryfall_card.artist_ids VARCHAR(2048) NULL`；`former_names` 以压缩 JSON 数组文本保存到 `zhs_oracle.former_names LONGTEXT NULL`。两者均不建立关联表或索引。
- `preview` 不参与检索，以规范 JSON 文本存入 `scryfall_card.preview` 的可空 `LONGTEXT` 列，不单独建表。
- `rulings.jsonl` 的每条规则使用规范化英文 `comment` 的 SHA-256 生成 `ruling_key`；规范化只统一换行、弯引号、不换行空格和首尾空白，正文不折叠或改写。
- `scryfall_oracle_ruling` 使用自增 `id` 区分每一条源记录，并保存 `oracle_id`、`ruling_key`、来源和发布日期；`zhs_ruling` 保存英文规则及中文翻译。Scryfall 中存在但中文文件缺失的规则必须补成 `translation NULL` 的英文行，已有中文翻译不得被覆盖。
- `rulings.jsonl` 中同一 `oracle_id` 和正文可能因不同发布日期而重复出现；所有源记录必须分别保留，不得覆盖或合并。自增 `id` 只作为本次加载结果的内部行标识，业务关联仍使用 `oracle_id` 和 `ruling_key`。
- `zhs_ruling.extra` 接受任意合法 JSON 值并以压缩 JSON 文本保存到 `LONGTEXT`，不建立 JSON 子表。
- `oracle-tags.jsonl` 只导入 `oracle` 标签。标签主表仅保留标签 ID、名称、说明和逗号连接的别名，不保存 Scryfall URI、slug、对象类型等本系统不用的元数据。
- `parent_ids` 和 `child_ids` 统一展开为 `oracle_tag_relation(parent_tag_id, child_tag_id)`，来自两个方向的相同关系去重；卡牌标签展开为 `oracle_tagging(oracle_id, tag_id, weight)`，`weight` 原样保存且不使用字典或枚举限制。
- 颜色、语言、布局、卡框、卡框效果、工艺和游戏平台的代码与说明由 Scryfall 官方元数据生成小型只读字典；卡牌主表保存代码或位掩码。
- 系列信息从 `scryfall_card` 的 `set_id`、`set_code`、`set_name`和 `set_type` 动态汇总到 `scryfall_set`，卡牌主表仅保留 `set_id` 关联。
- `cmc`、`mana_cost`、`type_line`、牌名、稀有度和发行日期保留在 `scryfall_card` 主表；`cmc`、`mana_cost`、牌名、稀有度和发行日期建立普通索引，类别筛选使用派生的 `scryfall_card_type` 表。
- 主键、翻译关联键和常用查询字段必须建立索引。全量原子换表不建立跨表外键约束，关联完整性由预检和业务查询保证。
- JSON 的 `null` 原样写入 MySQL `NULL`。
- 除上述明确的位掩码、`produced_mana` 字符串连接、字典关联和检索派生字段外，卡牌原始标量值不做业务转换。
- 普通、闪卡和蚀刻闪的计数归类只发生在业务查询层，不写回卡牌库。
- 使用批量插入，并记录每个文件的读取行数和插入行数。
- 解析或插入失败时需要记录文件名和行号，但不得记录完整卡牌 JSON。
- 同一服务实例同一时间只允许执行一个加载任务。
- 加载任务必须在开始、阶段切换、逐文件校验完成、逐文件导入完成、行数核对、原子切换和最终结果时输出结构化日志；任务运行期间每 30 秒输出一次包含任务 ID、当前阶段、当前文件和累计行数的心跳日志。批量写入过程不按固定行数额外输出进度日志。

### 15.8 接口行为

建议接口：

```http
POST /api/v1/card-data/load
```

该操作使用异步任务：

- 启动成功返回 `202 Accepted` 和任务 ID。
- 已有任务执行时返回 `409 Conflict`。
- 任务状态至少包括：`validating`、`preparing`、`importing`、`verifying`、`switching`、`completed`、`failed`。
- 提供按任务 ID 查询状态的接口。
- 失败结果需要包含失败阶段、文件名、行号和错误摘要。

当前不实现完整用户认证，但该接口必须具备最低限度保护：

- 默认关闭，通过配置显式启用。
- 请求必须携带固定确认文本 `LOAD_CARD_DATA`。
- 不允许请求指定数据库名、表名或文件路径。
- 部署时应只向内网或受反向代理限制的管理路径开放。

### 15.9 日志边界

卡牌数据加载属于系统维护任务，不计入用户操作日志。

任务结果至少记录：

- 任务 ID。
- 开始时间和结束时间。
- 每个文件的大小、SHA-256、预检行数和插入行数。
- 新旧表切换结果。
- 最终状态和错误摘要。
